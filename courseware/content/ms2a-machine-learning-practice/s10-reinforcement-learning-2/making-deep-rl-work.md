# Making Deep RL Work

A supervised model that does not learn has a bug you can find. An RL agent that
does not learn has thirty plausible causes and no loss curve that tells you
which. This lesson is the machinery and the discipline that make the difference.

## Why this is structurally harder

- **The data distribution moves.** Your training set is generated by the model
  you are training. Nothing in Sessions 3 to 8 has that property.
- **There is no loss to watch.** The TD loss can fall while the return falls —
  it measures self-consistency, not performance. The only honest metric is
  episode return, and it is noisy.
- **Everything is coupled.** Exploration shapes the data, the data shapes the
  value estimates, those shape the policy, and the policy shapes exploration.
- **Failures are silent.** A wrongly wired reward, an unnormalised observation
  and a learning rate ten times too high all look identical: a flat curve.

---

## Seed variance is not noise around the answer

Run the same algorithm, same hyperparameters, same environment, five different
seeds. On a typical continuous control benchmark, the best and worst seeds
differ by more than two published algorithms differ from each other.

Henderson et al. (2018) made this the standard objection to the deep RL
literature of the time, and it holds today. A single-seed comparison between
two configurations is worthless, and reporting the best of three seeds reports
the maximum of three samples, not the performance of your method.

Five seeds is the floor. Ten is defensible.

## Vectorized environments

The environment step is usually the bottleneck, and it is embarrassingly
parallel — the first thing to fix.

```python
envs = gym.make_vec("CartPole-v1", num_envs=16,
                    vectorization_mode="async")
obs, info = envs.reset(seed=0)
obs, rewards, terminations, truncations, infos = envs.step(actions)
```

Every array gains a leading `num_envs` axis, so the policy runs one batched
forward pass for 16 states instead of 16 — which is what a GPU is for.

`async` runs each environment in its own process — use it for anything
non-trivial. `sync` steps them in a loop in one process: right for a cheap
environment where process overhead dominates, and for debugging, because a
traceback from a subprocess is much less pleasant.

## Autoreset, and the trap in it

Vector environments reset a finished sub-environment automatically. In
Gymnasium 1.x the terminating step still returns the **true final
observation**; the reset observation arrives on the *next* step, where
`terminated` and `truncated` are both False and the reward is 0. That extra
transition is not a real transition — skip it when you write to the buffer.

```python
mask = ~prev_done                    # prev_done = done flags from the last step
buffer.add(obs[mask], action[mask], reward[mask], next_obs[mask], terminated[mask])
prev_done = terminated | truncated
```

Bootstrapping the value of the final observation is wrong for a genuine
termination and right for a time-limit truncation — a CartPole episode cut at
500 steps had a real future, it was just not shown to you. Gymnasium separates
`terminated` from `truncated` so you can tell them apart: cut the bootstrap on
`terminated`, keep it on `truncated`. Backwards, and the agent learns to end
episodes.

## Normalise observations

Networks in Session 4 wanted inputs of roughly unit scale. RL gives you a
LiDAR reading in metres next to an angular velocity in radians per second.

```python
env = gym.wrappers.NormalizeObservation(env)
env = gym.wrappers.TransformObservation(
    env, lambda o: np.clip(o, -10, 10), env.observation_space)
```

The wrapper keeps a running mean and variance and standardises with them.
Those statistics are learned parameters: save them with the checkpoint and
**freeze them at evaluation and at deployment**. An agent evaluated with
different normalisation statistics than it trained with scores near random, and
the checkpoint looks corrupt when it is fine.

---

## Normalise rewards, carefully

Reward scale sets the scale of the value targets, which sets the effective
learning rate of the critic. A return in the thousands makes the value loss
dominate everything. `NormalizeReward` divides by a running estimate of the
standard deviation of the discounted return; it does not subtract the mean,
which would change the sign structure the policy gradient depends on.

Reward *clipping* to $[-1, 1]$ is a different intervention — it changes the
problem, making all rewards equally important. Standard on Atari, wrong on
anything where magnitude carries information, such as a trading environment.

## Frame stacking and action repeat

An image is not a state: one frame of Pong does not say which way the ball is
moving, so the MDP assumption fails and no amount of training fixes it.

```python
env = gym.wrappers.FrameStackObservation(env, stack_size=4)
```

Stack the last four frames into the channel dimension and velocity becomes
observable. **Action repeat** (frame skip) holds each chosen action for $k$
frames, typically 4: it cuts the decision count by 4, shortens the credit
assignment horizon by 4, and is one of the largest single speed-ups available
on pixel-based environments. Both are wrappers; neither is part of your
agent.

## Sizing and stability

| Setting | Default | Reason |
|---|---|---|
| MLP hidden layers | 2 × 64 for states, 2 × 256 for hard tasks | RL overfits with capacity |
| Activation | tanh for PPO, ReLU for DQN/SAC | tanh bounds activations, which helps on-policy |
| Optimizer | Adam, `eps=1e-5` | the default 1e-8 is unstable here |
| Gradient clip | global norm 0.5 | a single bad batch can wreck a policy |
| Orthogonal init | gain 0.01 on the policy head | starts the policy near uniform |
| Learning rate | 3e-4, annealed to 0 | |

Bigger networks are not better in RL the way they are in Sessions 5 to 8. Two
hidden layers of 64 units solve most classic control tasks; a ten-layer network
is simply slower and less stable.

## Evaluation done right

Training returns come from an exploring, non-stationary policy, on episodes
interrupted by rollout boundaries. A progress signal, not a result.

- A **separate evaluation environment**, never the training one.
- The **deterministic** policy — the distribution mode, not a sample.
- Frozen normalisation statistics, 10+ episodes per point, 5+ training seeds.
- Report a **band**, not a line.

```python
mean, std = evaluate_policy(model, eval_env, n_eval_episodes=20,
                            deterministic=True)
```

## Report a band

```python
runs = np.stack([returns_for(seed) for seed in SEEDS])   # (n_seeds, n_points)
mu = runs.mean(0)
half = 1.96 * runs.std(0, ddof=1) / np.sqrt(len(SEEDS))
plt.fill_between(steps, mu - half, mu + half, alpha=0.2)
```

$$
\bar{x} \pm 1.96 \, \frac{s}{\sqrt{n}}
$$

Say in the caption which it is: standard error across seeds, standard deviation
across seeds and range across episodes are three different bands and are not
comparable. With five seeds the normal approximation is generous — draw the
individual seed curves as thin lines behind the band and let the reader see the
spread.

## Reproducibility

```python
random.seed(s); np.random.seed(s); torch.manual_seed(s)
torch.use_deterministic_algorithms(True)
obs, info = env.reset(seed=s)
env.action_space.seed(s)
```

Four generators, and the last is the forgotten one: `action_space.sample()` has
its own, so an unseeded action space makes your random baseline
irreproducible.

Even with all four, a GPU run is not bit-reproducible across driver versions and
an async vector environment interleaves episodes non-deterministically. Seed
everything anyway, log the seed with the result, and treat exact reproduction as
a nice-to-have and *statistical* reproduction as the requirement.

## The debugging ladder

Climb it in order. Do not skip a rung because it "obviously" works.

1. **Does a random agent score what you expect?** Run 100 episodes of
   `action_space.sample()` and write the number down. It is your floor, and it
   catches a broken environment before you blame the algorithm.
2. **Does the reward arrive where you think?** Print `(obs, action, reward)`
   for one episode and read it. A reward that is always 0, or always 1, or
   arrives one step late, is the single most common cause of no learning.
3. **Does it learn a trivial task?** Point your exact training script at
   CartPole. If it cannot reach 500 there, the bug is in your code, not in your
   environment or your hyperparameters.
4. **Can it overfit one episode?** Fix the seed and train on a single
   trajectory. A correct implementation drives the loss to near zero.
5. **Only now** tune hyperparameters.

## Use Stable-Baselines3

```python
from stable_baselines3 import PPO
from stable_baselines3.common.env_util import make_vec_env

envs = make_vec_env("CartPole-v1", n_envs=16, seed=0)
model = PPO("MlpPolicy", envs, n_steps=1024, batch_size=256, seed=0)
model.learn(total_timesteps=200_000)
model.save("ppo_agent")
```

Build the batch with SB3's own `make_vec_env`, not with `gym.make_vec`. SB3
takes its own `VecEnv`, and handing it a Gymnasium `VectorEnv` raises
`ValueError: The environment is of type ... not a Gymnasium environment` before
a single step runs.

SB3 is tested, benchmarked, and has the twenty undocumented details right —
advantage normalisation, orthogonal init, the Adam epsilon, the autoreset
bootstrap. Its defaults are a real baseline, not a placeholder. Write your own
when you are learning the algorithm, when you need to change the update rule,
or when your environment does not fit the Gymnasium interface — not because you
want a different network, which is a `policy_kwargs`.

> Implement PPO once, from the paper, to understand it. Then use the library
> for anything you intend to report.

## Check yourself

1. Run this. You should get exactly the output shown.

   ```python
   import gymnasium as gym, numpy as np
   envs = gym.make_vec("CartPole-v1", num_envs=1)
   obs, _ = envs.reset(seed=0)
   for t in range(20):
       obs, r, term, trunc, _ = envs.step(np.array([0]))
       if term[0] or trunc[0]:
           print("terminating step:", t, r[0], term[0])   # -> terminating step: 10 1.0 True
           obs, r, term, trunc, _ = envs.step(np.array([0]))
           print("next step:", r[0], term[0], trunc[0])   # -> next step: 0.0 False False
           break
   ```

   **Answer.** The terminating step carries the real final observation and a
   real reward. The step after it is the autoreset: reward 0, both flags False.
   Writing that one into the replay buffer teaches the agent that the state
   after death is worth something.

2. Your TD loss is falling steadily and the episode return is flat. Is the run
   working?

   **Answer.** No — and the loss cannot tell you. The TD loss measures
   self-consistency, not performance. The only honest metric in RL is episode
   return, evaluated on a separate environment with the deterministic policy.

3. You trained with `NormalizeObservation` and your saved agent scores near
   random at evaluation, though the checkpoint looks fine. What happened?

   **Answer.** The wrapper's running mean and variance are learned parameters.
   They must be saved with the weights and **frozen** at evaluation and
   deployment; an agent evaluated under different normalisation statistics than
   it trained with is being fed a different observation space.

4. Your agent does not learn. What are the first three rungs of the debugging
   ladder, in order?

   **Answer.** (1) Does a random agent score what you expect — 100 episodes of
   `action_space.sample()`, write the number down. (2) Does the reward arrive
   where you think — print `(obs, action, reward)` for one episode and read it.
   (3) Does your exact script learn CartPole. Hyperparameters are rung five.
